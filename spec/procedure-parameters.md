## Why

A package's manifest gives each exported procedure a signature with the parameters' types, not their names. So the Miden Playground labels a procedure's arguments `param_0`, `param_1` in its Simulate tab and its Invoke dialog, and the web-viewer finds the names by searching the Rust source with regular expressions (`apps/web-viewer/src/lib/procedure-signatures.ts`).

The names are in the package. `cargo-miden` embeds the component's public WIT, as text, in a package section named `wit` (`PACKAGE_WIT_SECTION_ID` in `midenc-frontend-wasm-metadata` 0.15.0). Seen in the Playground's Miden Bank example (`bank-account.masp`):

```
// This file is auto-generated by the `#[component]` macro.
package miden:bank-account@0.1.0;

use miden:base/core-types@1.0.0;

interface bank {
    use core-types.{account-id, asset, felt, word};

    initialize: func();
    get-depositor-balance: func(depositor: account-id, asset: asset) -> felt;
    deposit: func(depositor: account-id, deposit-asset: asset);
    withdraw: func(withdraw-asset: asset, serial-num: word, tag: felt, note-type: felt);
}
```

A note has one too (`%run: func(arg: word);`). So `miden-package-metadata` can report the names as it reports `readOnly` and `callsForeign`, and packages the registry already stores can be filled from their `.masp` without a rebuild.

## Output contract

`miden-package-metadata` prints a new top-level key, next to `readOnly` and `callsForeign`, for every package kind: a map from export path to the procedure's parameters, in order.

```json
"parameters": {
  "::\"miden:bank-account/bank@0.1.0\"::deposit": [
    { "name": "depositor", "type": "account-id" },
    { "name": "deposit-asset", "type": "asset" }
  ],
  "::\"miden:bank-account/bank@0.1.0\"::initialize": []
}
```

- `name` and `type` are the WIT's, verbatim, in kebab case, as the fields of `noteStorage` are. Consumers convert for display. `type` is the type's name (`felt`, `account-id`), or its structural kind when it has none, as `type_name` does in `schemas.rs`.
- An export is in the map only when its WIT function was found **and** has as many parameters as the manifest's signature. A consumer can pair the two lists by index without checking.
- No names is one case, however it happens: an export missing from the map, a package without a `wit` section (`{}`), a section that doesn't parse (the key is absent), an older api-compile (the key is absent). It never fails a build.
- Room to grow: an entry can gain a `description` later without a new key. Result names and doc comments aren't in the WIT today.

## Checks to run first (stop and report if one fails)

1. **Parsing.** `wit-parser` 0.258 is already in the crates' lockfile, through `miden-note-schema`. The section `use`s `miden:base/core-types@1.0.0`, which it doesn't contain. Find out whether `wit-parser` gives the functions and their parameters without resolving that package (its unresolved AST), or how `miden-note-schema` (`src/schema.rs`, `src/section.rs`) supplies it. Don't write a WIT parser by hand.
2. **Matching.** An export's path is `::"<interface>"::<function>`, the function quoted when it has a dash: `::"miden:bank-account/bank@0.1.0"::"get-depositor-balance"`. Confirm that the pair matches the WIT's package, interface and function on five packages: the Playground's `bank-account`, `counter-account` and `count-reader` (`apps/api/examples` and `apps/api/templates` in miden-playground), a note and a transaction script. Notes escape the name (`%run`).
3. **Parameter counts.** On the same five, the WIT's count equals the manifest's `signature.params.length` for every export with the component-model ABI (`abi: 3`). If a type is flattened on one side only, report it: the contract's pairing rule depends on this.
4. **Stored packages.** Count the registry's packages whose `.masp` has no `wit` section, with a read-only pass over production's artifacts or a local copy. The answer decides step 14.

## Steps

### `miden-package-metadata`

5. A new module `src/parameters.rs`, in the style of `schemas.rs`: look the section up, parse it, and on failure write the reason to stderr and return `None`. `package(&Package) -> Option<Map>`: `None` for a section that can't be read, an empty map for a package without one.
6. `src/main.rs`: add `"parameters"` when the module returns `Some`, with a comment stating the contract. Declare the module. `Cargo.toml`: `wit-parser` at the version the lockfile already has.
7. Unit tests in the module, on small WIT sources placed in a package's section as `schemas.rs`'s tests do:
   - names and types of two procedures, one with no parameter;
   - a function with a dash in its name, and an escaped one (`%run`);
   - a count that differs from the signature's: the export is left out, the others stay;
   - no section: an empty map;
   - a section that isn't WIT: `None`, and nothing panics.

8. `packages/utils/src/manifest.ts`: `ProcedureParameter` and `ProcedureParameters`, documented like `ForeignCallingProcedures` (what an absent export and an absent key mean).
9. `packages/utils/src/api-compile.ts`: `parameters?: ProcedureParameters` on `BuiltPackage`. `apps/api-compile/src/lib/helper-tools.ts`: the same on `PackageMetadata`.
10. Pass it through wherever `callsForeign` is: `grep -rn callsForeign apps packages --include=*.ts` outside `dist` and the worker type files. ## Gotchas

- The section's id is a custom one today. The compiler plans an upstream `SectionId::WIT` (see the comment on `package_wit_section_id`): on a toolchain bump, re-check the id, as the `miden-package-metadata` crate's `Cargo.toml` pins the versions it reads.
- `preserve_order` is on for `serde_json`: build the map in the manifest's export order so the output is stable.
- A merge deploys every service at once. Between the web-viewer's deploy and the end of the backfill, a stored package has a null `parameters`: the web-viewer must render it (types only, or the source search) rather than fail.
- The Playground's example snapshots and stored packages don't have the key until they're recompiled. That is the Playground half's concern.

## Out of scope

- `callsForeign` in the registry: it isn't stored today.
- Result names and doc comments.
- The parameters of procedures a package imports from its dependencies.

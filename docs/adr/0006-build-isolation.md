# Builds run as an unprivileged user, and the shared target directory is closed by a read-only warm cache

**Accepted** (2026-11-11). Compiling a project runs its own code (`build.rs`, procedural macros), and today that code runs as root in the container every later request uses, with write access to the helper tools, the toolchain, the shared cargo target directory, the client stores and the parent of every project directory. One request can therefore change what later builds link, or make `POST /verify` answer `verified: true` for a package that isn't the resource's, an answer the registry records permanently. We take two steps. First (prototyped on `spike/build-isolation`, measured below): the server stays root and starts cargo as a `builder` user and the helper tools as an `api` user, so build code can write only its own project directory, `/cache/target` and `/cache/cargo-home`. Second (not prototyped): make `/cache/target` read-only and give each build a throwaway copy, which `cp -a` made of the 1.6 GB warm cache in 0.16 s inside the local container. This needs no privilege, so unlike an overlayfs mount (see below) it should also work on Cloudflare Containers, but that was not measured there. No option changes what a build's own code can do to its own result: a `build.rs` can emit any package, so a verification shows that these sources, built, produce the resource's package, and a reader judges the sources, `build.rs` included.

## Measurements

Baseline (image built from `main`, `docker exec` as the server's user; the server runs as uid 0): `/usr/local/cargo/bin`, `/usr/local/cargo/bin/miden-verifier`, `/usr/local/rustup`, `/cache/target`, `/cache` and `/tmp` are all writable. Prototype, checked as `builder`: only `/cache/target`, `/cache/cargo-home` and `/tmp` are writable; the toolchain, the helper tools, `/cache`, `/cache/stores`, `/work` and `/work/projects` are not. `/cache/stores` is writable by `api` only. Each project directory is `/work/projects/<random>`, mode 0700 and the build user's, under a root-owned 0711 parent, so no directory build code can write is a parent of another request's project.

The api-compile suite passes on the prototype (9 files, 93 tests). A warm `POST /compile` (`__tests__/compile.test.ts`, second run, 25 tests): 15.09 s on the baseline container and 14.90 s on the prototype, run back to back with nothing else building. Image size is unchanged at 3.33 GB; building the warm cache as `builder` avoids a `chown -R` layer that would duplicate it. `/cache/target` is 1.5-1.6 GB.

What the prototype needed that the plan didn't list: `CARGO_HOME` moves to `/cache/cargo-home`, because cargo writes its registry cache and a lock file under it (build code owning the toolchain's `/usr/local/cargo` would defeat the point); the warm-up builds a copy of the example, because the `miden::generate` macro writes a `target/` inside the project; and the Cloudflare wrangler config sets `MIDEN_CLIENT_CACHE_DIR=/cache`, which `api` can't write, so it must change to `/cache/stores` when this ships.

## Options for the shared target directory

- **B1, read-only warm cache plus a per-request copy.** Recommended as the second step. Cost: 0.16 s and 1.6 GB of disk per concurrent build (builds are serialised, so one copy at a time). Feasible in docker compose and, as a plain copy, on Cloudflare Containers. An overlayfs mount isn't: the container's default capabilities exclude `CAP_SYS_ADMIN` (a `mount` as root was denied here), and Cloudflare's architecture page says nothing about granting privileges (https://developers.cloudflare.com/containers/platform-details/architecture/). Residual: build code still runs, so it can attack the server through anything it can reach, and the copy's cost on `standard-2` disk is unmeasured.
- **B2, a fresh container per request.** Cloudflare documents cold starts "often in the 1-3 second range", and `destroy()` and `signal()` stop an instance (same page), but this repo's README records ~50 s for the cold start with this image, and `max_instances` is 1; a one-request-per-instance design needs more instances and a routing change. Not verified on Cloudflare; rejected for now on cost. It is the strongest option (nothing survives a request), and the upgrade path if the container ever holds secrets, or if a build taking the container down becomes a real problem: it gives kernel-level separation without running a sandbox ourselves. That rests on Cloudflare's documentation that each instance is a separate VM, which hasn't been verified here.
- **B3, verify-only hardening.** Run `/verify` builds against a pristine copy. It stops an earlier `/compile` request from poisoning a later verification, but it does nothing about the build being verified, whose code runs too, and it leaves every `/compile` answer exposed. B1 gives every build the same pristine start: rejected in its favour.
- **B4, detect instead of prevent.** Checksum the warm artifacts and helper tools at startup and before each `/verify`, restart on mismatch. Blind spots: an artifact changed and restored during a request, state outside the checksummed set (config files, the cargo registry, stores), and the cost of hashing 1.6 GB per `/verify`. Rejected as the primary defence.

## What remains exposed

After step one, the root server reads a build output (the `.masp`, the `.masm`, `Cargo.lock`) only when it is the build user's plain file: not a symlink, not hard-linked, reached through no symlinked directory, under the build's own directory. A planted link can't make it read another file. No build user process outlives its build: every one is killed after each `cargo miden build`, and before each build. `/tmp`, `/var/tmp` and `/dev/shm` lose the build user's entries at the same points, and the build's `HOME` and `TMPDIR` are a directory of the build that is deleted with it; `/home/builder` isn't writable. Both rest on one build at a time, so the server refuses to start with `COMPILE_CONCURRENCY` above 1 when builds run as their own user. What stays exposed until step two: `/cache/target` and `/cache/cargo-home`, including `/cache/cargo-home/config.toml`, which cargo reads on every build. Build code can also still use the network and the CPU.

This isolation is Unix users on the container's one kernel: a kernel exploit, or a bug in the root server, undoes it. A build's memory isn't bounded per build, only by the container's (6 GiB on `standard-2`). Processes are capped at 4096 per user (`RLIMIT_NPROC`, set on the server and inherited), so a fork bomb stops there. The image has no setuid or setgid binaries, the usual route from an unprivileged user back to root.

## Considered Options

- **Keep the container as is and rely on the 5-minute sleep.** Rejected: traffic keeps it awake.
- **Run the server as `api` and cargo through `setpriv`/`runuser`.** Rejected: needs root.
- **A single unprivileged user for everything.** Rejected: build code could then write the helper tools' client stores.
- **A sandbox per build (gVisor, nsjail/bubblewrap).** Rejected for now. Cloudflare Containers doesn't let us choose the runtime; the container can't `mount`; and user namespaces are refused (`unshare -Urn true` → `Operation not permitted`, as `builder` and as root, under Docker's default profile; unverified on Cloudflare), which also rules out cutting a build's network through a network namespace.

# Builds run as an unprivileged user, and the shared target directory is closed by a read-only warm cache

**Accepted** (2026-11-11). Compiling a project runs its own code (`build.rs`, procedural macros), and until this decision that code ran as root in the container every later request uses, with write access to the helper tools, the toolchain, the shared cargo target directory, the client stores and the parent of every project directory. One request can therefore change what later builds link, or make `POST /verify` answer `verified: true` for a package that isn't the resource's, an answer the registry records permanently. We take two steps. First (prototyped on `spike/build-isolation`, measured below): the server stays root and starts cargo as a `builder` user and the helper tools as an `api` user, so build code can write only its own project directory, `/cache/target` and `/cache/cargo-home`. Second (done since: the warm cache is built at its final paths, moved to a read-only `/cache/image` and copied back before each build): make `/cache/target` read-only and give each build a throwaway copy, which `cp -a` made of the 1.6 GB warm cache in 0.16 s inside the local container. This needs no privilege, so unlike an overlayfs mount (see below) it should also work on Cloudflare Containers, but that was not measured there. No option changes what a build's own code can do to its own result: a `build.rs` can emit any package, so a verification shows that these sources, built, produce the resource's package, and a reader judges the sources, `build.rs` included.

## Measurements

Baseline (image built from `main`, `docker exec` as the server's user; the server runs as uid 0): `/usr/local/cargo/bin`, `/usr/local/cargo/bin/miden-verifier`, `/usr/local/rustup`, `/cache/target`, `/cache` and `/tmp` are all writable. Prototype, checked as `builder`: only `/cache/target`, `/cache/cargo-home` and `/tmp` are writable; the toolchain, the helper tools, `/cache`, `/cache/stores`, `/work` and `/work/projects` are not. `/cache/stores` is writable by `api` only. Each project directory is `/work/projects/<random>`, mode 0700 and the build user's, under a root-owned 0711 parent, so no directory build code can write is a parent of another request's project.

The api-compile suite passes on the prototype (9 files, 93 tests). A warm `POST /compile` (`__tests__/compile.test.ts`, second run, 25 tests): 15.09 s on the baseline container and 14.90 s on the prototype, run back to back with nothing else building. Image size is unchanged at 3.33 GB; building the warm cache as `builder` avoids a `chown -R` layer that would duplicate it. `/cache/target` is 1.5-1.6 GB.

Step two, measured locally (aarch64): cargo's dependency fingerprints record the `CARGO_HOME` path, so the copy must sit at the paths the warm-up used; a copy at another path recompiled all 271 dependencies, ~48 s. With the cache built at its final paths, moved to a read-only `/cache/image` and copied back before each build, dependencies stay warm and commitments are unchanged. The copy of both directories takes 0.4-0.6 s (399-603 ms over 105 builds), and a counter-contract `POST /compile` goes from 0.46 s to 1.50 s: the copy, about 0.2 s to delete 1.8 GB, and cargo a little slower. The 25 tests of `compile.test.ts` take 45.79 s on the second run, against 15.77 s before. Production copy time is to be read from production logs after deploy.

Step three (2026-11-13): in production the copy cost about 9 s per build on `standard-2`, and a counter-contract `POST /compile` went from ~7 s cold / ~2 s warm to 34 s / 11.2 s, the cold one reading all 1.8 GB off a fresh disk. The server now hard-links what a build only reads (`*.rlib`, `*.rmeta`, `*.so` and `build_script_build` under the target directory, `registry/src` and `registry/cache` under `CARGO_HOME`: 18,945 files) and copies the rest (about 4,400 files, 63 MB), which cargo opens for writing: lock files, fingerprints, build script output, the registry index. A linked file stays root's and unwritable by others, so `builder` can replace it in its own directory (rustc and the linker do, when they rebuild an output) but not change it; only a file that is root's and not group- or other-writable is linked. Measured locally: both profiles stay warm with unchanged commitments; a build forced to recompile 106 crates, and one that relinks build scripts, over linked files gives the same package as over copies; the image's cache is byte-identical afterwards; a `build.rs` that opens every file of its cache it doesn't own for writing finds none (`compile.test.ts`). Laying the cache out takes 0.5-1.0 s locally, the same as the copy, where the disk is fast; the production figure is to be read after deploy. If linking fails (the two paths on different filesystems), the server falls back to the full copy.

Step four (2026-11-13): with hard links, production went to 11.7 s cold / 5.0 s warm, about 3 s of it laying the cache out and deleting it again: each build created and removed about 30,000 entries, 20,800 of them the crate sources (`registry/src`: 17,367 files in 3,435 directories). `registry/src/<registry>` is now the build user's directory holding one symbolic link per crate (409) to that crate's root-owned directory in `/cache/image`, so a build makes and deletes about 9,700 entries. Build code reaches the image's files themselves through those links, so the server first checks, once per process, that everything under the image's `cargo-home` is root's and not group- or other-writable (after that only root could change it), and falls back to the full copy otherwise. Cargo still unpacks a crate it downloads next to the links. Measured locally: no dependency recompiles and commitments are unchanged; a build forced to recompile all 276 crates in both profiles (`codegen-units` overridden for every package) gives the same release and debug commitments as on `main`, and neither package names `/cache/image`; the probe `build.rs` follows the links and finds 22,378 files and directories it doesn't own, none it can write. A warm counter-contract `POST /compile` goes from 1.9 s to 1.06 s (layout 0.78 s to 0.31 s, cleanup about 0.15 s). `POST /compile` now answers with a `Server-Timing` header (`layout`, `cargo`, `tools`, `debug`, `cleanup`, in ms), since the container's log can't be read from the CLI.

Step four in production (container v102, 2026-11-13, counter-contract, read from the header): warm, 3.8-4.7 s over six requests against 5.0 s before: layout 1.13-1.22 s, cargo 1.27-1.47 s, tools 0.05 s, cleanup 0.61-0.69 s, and 0.7-0.9 s the header doesn't cover (the network, the Worker, the process sweeps, writing the project). The links saved about 1 s per build, not the 2 s expected, and laying the cache out and deleting it is still about 1.85 s of a warm request. Cold (first request after the container slept), two samples: 15.9 s and 13.1 s against one 11.7 s sample before, with layout 5.95 s and 4.58 s, cargo 5.92 s and 4.57 s, cleanup 0.7 s, and about 3 s for the wake and the rest. A cold start is no faster and may be slower: the first layout includes the once-per-process walk of the crate sources, which reads every entry off the fresh disk; whether that walk is the difference isn't measured. Cargo compiled only the project in every request, so the links cause no recompile on x86_64, and every answer had the expected commitment.

Step five (2026-11-13): the layout and the cleanup, about 1.85 s of a warm request in production, leave the response path. When a build's answer is ready, the server starts, without waiting for it, what the next build needs: it deletes the project, kills the build user's processes, and replaces the build's view of the cache (its package included) with a new one. The next build waits for that, so the order is unchanged: no build starts before the previous one's files are gone, and no build user process is alive while a view exists. What changes is that an unused view now sits on disk between requests, where each build's view used to be deleted before its answer; no build code has run in it. A view serves one build; the first build of a process, and one that follows a failed preparation, lay out their own as before, and a failure there fails the request. The sweep that kills the build user's processes signals every such process but itself, another sweep included, so it runs once per view and no longer at the start of each build; when it fails after a build, no view is prepared, so a surviving process has none to itself while the server is idle, and the next build sweeps again and lays out its own. A request whose client left while it waited takes no view, and on `SIGTERM` the server waits for the work after the last build before it exits. Measured locally: a counter-contract `POST /compile` on a server idle for 2 s takes 0.61-0.71 s against 1.05 s (`layout;dur=0`); back to back, 0.97-0.99 s, the build waiting about 0.33 s for a view that takes about 0.5 s to prepare (`prepare` in the header).

Step five in production (container v103, 2026-11-13, counter-contract, read from the header): on a server idle for 1 s or more, 2.0-2.4 s over eight requests (one at 2.7 s) against 3.8-4.7 s before, with `layout` 0, cargo 1.22-1.33 s and 0.7-1.0 s the header doesn't cover. With no gap between requests, 3.1-3.2 s: the build waits 1.07-1.24 s for a view that takes 1.7-2.2 s to prepare. `GET /` answers in about 0.1 s while a view is being prepared. Cold, one sample: 21.3 s (layout 9.2 s, cargo 8.2 s), against 15.9 s and 13.1 s after step four and 11.7 s before it. Cold starts vary by seconds from one to the next and this step doesn't touch the first layout, so the three steps' cold figures can't be ranked from four samples; none of them made a cold start faster. The two requests right after that cold start took 3.9-4.1 s with `layout` 0, about 1.5 s more than later ones, unexplained.

What the prototype needed that the plan didn't list: `CARGO_HOME` moves to `/cache/cargo-home`, because cargo writes its registry cache and a lock file under it (build code owning the toolchain's `/usr/local/cargo` would defeat the point); the warm-up builds a copy of the example, because the `miden::generate` macro writes a `target/` inside the project; and the Cloudflare wrangler config sets `MIDEN_CLIENT_CACHE_DIR=/cache`, which `api` can't write, so it must change to `/cache/stores` when this ships.

## Options for the shared target directory

- **B1, read-only warm cache plus a per-request copy.** Recommended as the second step; since step three most of the copy is hard links, and since step four the crate sources are symbolic links (see Measurements). Cost as estimated before step two: 0.16 s and 1.6 GB of disk per concurrent build (builds are serialised, so one copy at a time). Feasible in docker compose and, as a plain copy, on Cloudflare Containers. An overlayfs mount isn't: the container's default capabilities exclude `CAP_SYS_ADMIN` (a `mount` as root was denied here), and Cloudflare's architecture page says nothing about granting privileges (https://developers.cloudflare.com/containers/platform-details/architecture/). Residual: build code still runs, so it can attack the server through anything it can reach, and the copy's cost on `standard-2` disk was unmeasured (about 9 s, see step three).
- **B2, a fresh container per request.** Cloudflare documents cold starts "often in the 1-3 second range", and `destroy()` and `signal()` stop an instance (same page), but this repo's README records ~50 s for the cold start with this image, and `max_instances` is 1; a one-request-per-instance design needs more instances and a routing change. Not verified on Cloudflare; rejected for now on cost. It is the strongest option (nothing survives a request), and the upgrade path if the container ever holds secrets, or if a build taking the container down becomes a real problem: it gives kernel-level separation without running a sandbox ourselves. That rests on Cloudflare's documentation that each instance is a separate VM, which hasn't been verified here.
- **B3, verify-only hardening.** Run `/verify` builds against a pristine copy. It stops an earlier `/compile` request from poisoning a later verification, but it does nothing about the build being verified, whose code runs too, and it leaves every `/compile` answer exposed. B1 gives every build the same pristine start: rejected in its favour.
- **B4, detect instead of prevent.** Checksum the warm artifacts and helper tools at startup and before each `/verify`, restart on mismatch. Blind spots: an artifact changed and restored during a request, state outside the checksummed set (config files, the cargo registry, stores), and the cost of hashing 1.6 GB per `/verify`. Rejected as the primary defence.

## What remains exposed

After step one, the root server reads a build output (the `.masp`, the `.masm`, `Cargo.lock`) only when it is the build user's plain file: not a symlink, not hard-linked, reached through no symlinked directory, under the build's own directory. A planted link can't make it read another file. No build user process outlives its build: every one is killed after each `cargo miden build`, and before each build. `/tmp`, `/var/tmp` and `/dev/shm` lose the build user's entries at the same points, and the build's `HOME` and `TMPDIR` are a directory of the build that is deleted with it; `/home/builder` isn't writable. Both rest on one build at a time, so the server refuses to start with `COMPILE_CONCURRENCY` above 1 when builds run as their own user. Build code can also still use the network and the CPU. Within one request, the debug build reuses the cache the release build used, so a build can still affect its own debug variant (the build's own result).

This isolation is Unix users on the container's one kernel: a kernel exploit, or a bug in the root server, undoes it. A build's memory isn't bounded per build, only by the container's (6 GiB on `standard-2`). Processes are capped at 4096 per user (`RLIMIT_NPROC`, set on the server and inherited), so a fork bomb stops there. The image has no setuid or setgid binaries, the usual route from an unprivileged user back to root.

## Considered Options

- **Keep the container as is and rely on the 5-minute sleep.** Rejected: traffic keeps it awake.
- **Run the server as `api` and cargo through `setpriv`/`runuser`.** Rejected: needs root.
- **A single unprivileged user for everything.** Rejected: build code could then write the helper tools' client stores.
- **A sandbox per build (gVisor, nsjail/bubblewrap).** Rejected for now. Cloudflare Containers doesn't let us choose the runtime; the container can't `mount`; and user namespaces are refused (`unshare -Urn true` → `Operation not permitted`, as `builder` and as root, under Docker's default profile; unverified on Cloudflare), which also rules out cutting a build's network through a network namespace.

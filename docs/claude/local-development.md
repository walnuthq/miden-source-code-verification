# Local development

The docker compose stack (`docker compose up -d --build`) is the normal way to run api-compile, api-registry and postgres: the suites test it, and its `api-registry-migrate` service runs the migrations. The notes below are for everything outside it.

- Check web-viewer and web-verifier changes against their dev servers (`pnpm --filter ./apps/<app> dev`, with hot reload), not by rebuilding the compose images after each change. Start the dev server once and keep it running across edits; the API containers stay in docker. Rebuild a container only when its Rust crate changes.
- Running api-compile on the host needs the three helper tools (`miden-import`, `miden-package-metadata` and `miden-verifier`) on `PATH`, built from `apps/api-compile/crates` (`cargo build --release --locked --workspace`, about 3 min warm and 20 min cold), then copied into `~/.cargo/bin` or run with the crates' `target/release` first on `PATH`. Nothing rebuilds them when the crates change, unlike the Docker image, so a copy goes stale silently: `unsupported version. Got '[7, 0, 0]'…` from miden-package-metadata, `Wrong number of arguments` from miden-verifier, or `unsupported network ID` for a network added since. Run `which miden-package-metadata` with that `PATH` before starting the server: a missing `target/` dir falls back to `~/.cargo/bin` without a word.
- Give a host api-compile a fresh `MIDEN_CLIENT_CACHE_DIR`, and `mkdir -p` it right before a test run. An old miden-client store there fails with `stored schema at version 1 does not match…`, and a deleted cache dir shows up as `spawn miden-verifier ENOENT` (502 on verify and import), which looks like a missing binary but isn't: the tools run with that dir as `cwd`. They keep one store per network under it (`<cache>/mtst/`, `<cache>/mdev/`, …).
- A host api-registry needs `ADMIN_TOKEN` (compose uses `dev-admin-token`), or the admin debug-build tests get 404s, and `API_COMPILE_URL` pointing at the api-compile it should call. Point the suites at host servers with `API_URL`.
- `wrangler dev` in `apps/api-compile-cloudflare` builds `apps/api-compile/Dockerfile` for linux/amd64, under emulation on Apple Silicon and without the compose build cache: a cold build takes over an hour. To check container or egress behaviour, a scratch Worker with the same `@cloudflare/containers` `Container` class, the same compatibility date and a `busybox httpd` Dockerfile takes minutes. Symlink its `node_modules` to the repo root's: deps are hoisted, and apps have no `node_modules/.bin`.
- Stopping `wrangler dev` can leave `…-proxy` sidecar containers running (workers-sdk #14242); remove only the ones your own test created. If containers fail to start with `setsockoptint`, see cloudflare/cf-platform-issues#52.

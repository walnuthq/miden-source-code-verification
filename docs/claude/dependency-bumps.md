# Dependency bumps

Some bumps have rules of their own: `drizzle-kit` needs the `check`/`up` steps in `database-migrations.md`; a `cargo update` of the examples' lockfiles needs the Playground resync and the offline check in `warm-lockfile.md`; the corepack pin lives in all four Dockerfiles (CODING_STANDARDS.md). `@types/node` follows the Node major, with nothing held back.

- pnpm applies a minimum release age of about 24 h by default, with nothing set in `pnpm-workspace.yaml`. Pinning a version younger than that makes `pnpm install` succeed but silently add `minimumReleaseAgeExclude:` entries for the package and its too-new dependencies to `pnpm-workspace.yaml`; once that is reverted, installs fail with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` until the lockfile entries are gone. The exclusion turns off a supply-chain guard, so check `git diff pnpm-workspace.yaml` before committing and ask rather than commit one; staying one version back is the usual answer. Check `npm view <pkg> time` against now minus 24 h first. To back out: `git checkout pnpm-lock.yaml pnpm-workspace.yaml`, set the older pin, then `pnpm install`, which re-resolves only the changed pins.
- After a `packageManager` bump, pnpm in the repo fails with `the installed pnpm wrapper is missing at …` when the new version isn't cached locally: `nodeLinker: hoisted` leaks into pnpm's engine download. The setting is required (see the comment in `pnpm-workspace.yaml`); CI (`pnpm/action-setup`) and Docker (corepack) install the pinned version directly and are unaffected. Prime the version from outside the repo first by running `pnpm --version` in a scratch dir with only `{"packageManager":"pnpm@<ver>"}` and no workspace yaml, then bump with `corepack use pnpm@<ver>` in the repo. Updating the global pnpm to the same version also works. `corepack install -g pnpm@<ver>` isn't reliable: it primed 12.17.0 but not 12.18.0, where the error came back.

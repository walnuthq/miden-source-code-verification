# api-compile's warm lockfile

The image warms cargo's cache from `apps/api-compile/examples/counter-contract/counter-contract/Cargo.lock`, which every example's lockfile matches, and builds run `--offline` first. Miden Playground (walnuthq/miden-playground) sends its own lockfile, `apps/api/templates/project-template/Cargo.lock`, which must pin the same registry crates.

- After a `cargo update` of the examples' lockfiles (or a toolchain bump), run `pnpm lockfile:sync` in the playground's `apps/api` against the new image, and ship both together. Otherwise every playground build downloads and rebuilds the crates that differ (176 s on production, lost each time the container sleeps).
- `GET /lockfile` serves the warm lockfile (`WARM_CARGO_LOCK`), for that check.
- `POST /compile` with `warmLockfile: true` re-resolves a lockfile that fails offline (`cargo update --offline`) before building online, and returns the updated lockfile. `/verify` and `/compile-debug` never do: they must build the exact lockfile they're sent.
- The offline-first build breaks silently when a warmed crate is yanked: locked builds still accept it, but a request without a lockfile resolves fresh, finds no alternative offline ("failed to select a version … is yanked"), falls back online and recompiles the whole tree, minutes on the container. Nothing errors and no test sees it. After bumping the examples' lockfiles or rebuilding the image, check in a throwaway container of the image, not in the running server (which replaces `/cache/target` and `/cache/cargo-home` on every build): `docker run --rm --user root --entrypoint sh <image>`, then as root `mkdir /cache/target /cache/cargo-home && chown builder:builder /cache/target /cache/cargo-home`, and as `builder` copy `/cache/image/target/.` and `/cache/image/cargo-home/.` into them with `cp -a`, copy the counter-contract example out of `/cache/examples` to a scratch directory, delete its `Cargo.lock`, and run `cargo miden build --release --offline` there as `builder` with the `CARGO_TARGET_DIR`/`MIDENC_TARGET_DIR` of the Dockerfile's warm-up step. It must succeed in about a second and reproduce the committed lockfile. To replace a yanked pin, `cargo update -p <crate> --precise <older>` in every example lockfile, and compare package commitments between the two versions first (not `.masp` bytes, which differ by path metadata): unchanged commitments mean no fixture regeneration.

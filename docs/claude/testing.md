# Testing

The api-compile and api-registry suites call whatever is listening on `localhost:8080`/`8081` (`API_URL` overrides): normally the docker compose stack. To test a server change, rebuild and restart it first (`docker compose up -d --build`), or the suites test the old images.

API tests use `request()` from `miden-source-code-verification-test-utils` (a fetch-based, supertest-like builder), not supertest.

Tests are typechecked with the same strictness as the sources, by each package's `typecheck` and so by `pnpm check`. In the Node packages (api-compile, api-registry, utils) `tsconfig.json` is the check-only config (`noEmit`, sources plus `__tests__` and the config files) and `build` runs `tsconfig.build.json`, which narrows to `src` and emits. The Vite apps check `__tests__` in a third referenced project, `tsconfig.test.json`; their `build` names only the app and node projects, since the Docker build context has no `__tests__`. To change a file of a `readProjectFiles` result before sending it, use `editProjectFile(files, path, edit)`, and `projectFile(files, path)` to only read one: both throw on a missing file, where indexing the record gives `string | undefined`.

Fixtures (`packages/test-utils`) live on Testnet only. Mainnet (`mm`, Miden's invite-only Partner Mainnet) has none: creating an account there needs an invite code and costs real fees, so don't deploy to it. Mainnet tests only read the public USDCx fee faucet (`0xe69e6ca6e39df1b10c1e5399399feb`). Use `mxx` for a network the binaries don't serve: `mlcl` resolves on the host but not in the container.

`pnpm --filter miden-source-code-verification-test-utils generate-fixtures` (defaults to `mtst`) rewrites all of `packages/test-utils/src/fixtures.ts`: every id, the `accounts` map and the `notes` map. It deploys two counter-contract accounts, a note factory and a funder wallet, creates the public counter and increment notes, and funds everything from the testnet faucet, so it is a deliberate, outward-facing action: confirm before running it unless the user asked for it. It takes about 20 min (cargo-miden builds each example in its own temp target dir first) and writes the file only at the very end, so a transient testnet RPC timeout (`sync_chain_mmr: Timeout expired`) near the end loses the run; a plain retry worked.

- Regenerate the fixtures when the serialization format or the compiler output changes (a Miden upgrade once made older blobs fail with `Unsupported version. Got '[0, 0, 3]'`): the api-compile and api-registry suites and the status-page probe verify against them on chain.
- Validate changes to the generator, or any tool that deploys throwaway accounts or notes, on devnet (`--network-id mdev`) with the output somewhere scratch. Testnet is where the committed fixtures live, and every suite uses `mdev` as the network a fixture must not exist on. Check first that devnet's node version accepts the client's: a release-candidate node once rejected it outright ("server rejected request - please check your version and network settings").
- Fixture accounts are funded from the public faucet (`https://faucet-api.<network>.miden.io`) by a throwaway funder wallet and pay their fee with a `TxFeeNote`. Nodes since 0.16 reject any transaction with no non-zero fee note where `verification_base_fee` isn't 0, so a fee-free auth component is not an answer to a fee error; the tool only skips funding where the base fee is 0.
- Faucet 0.17 owns no account: `/get_tokens` forwards to the node's funding service and returns only `{ "note_id" }`. If `fee::fund` hangs, check `https://status.testnet.miden.io` for blocks still being produced before blaming the tool.
- The registry reaches api-compile through the `ApiCompile` port `createApp` attaches to the app (`apps/api-registry/src/lib/api-compile.ts`). An in-process test, one that calls `createApp()` or `verifyResource` directly, passes `fakeApiCompile({ … })` from `apps/api-registry/__tests__/fake-api-compile.ts` as `apiCompile` with the calls it expects; don't `vi.mock` the module. A verification calls only `verify`, whose answer carries the resource's `root`; the id-keyed lookups call `importResource`. Tests that query the compose stack need nothing: its api-compile is real.
- A test that runs a helper tool in-process (the import route, `verify`) fakes it with `useFakeTool(name, script)` from `apps/api-compile/__tests__/fake-tool.ts`: a shell script named after the tool, first on `PATH` for the describe it's called in, that behaves as its arguments say. The file also mocks `MIDEN_CLIENT_CACHE_DIR` to `os.tmpdir()`, since `miden-import` and `miden-verifier` run with it as `cwd` and the host has no `/cache`. Don't `vi.mock` `lib/helper-tools.ts`. The runner's rules (exit 2, exit 1, timeout, not installed, nothing or no JSON printed) are covered once in `helper-tools.test.ts`; a caller's test covers only its own mapping (ok, rejected, failed).
- `apps/api-compile/__tests__/helper-tools.test.ts` mocks `MIDEN_TOOL_TIMEOUT_MS` to 3 s. Under a full parallel `pnpm test`, a cold exec of the fake script under load has exceeded the mocked timeout (at 500 ms, in the import tests it replaced, and at 1 s on 2026-11-13) and failed the first cases, which passed alone. If only these fail, rerun `pnpm exec vitest run __tests__/helper-tools.test.ts` in `apps/api-compile` before blaming a change; if it keeps recurring, raise that mocked timeout.
- The web-viewer suite (`apps/web-viewer/__tests__`, vitest) is pure: the pure functions, and the page-data module `lib/resource-page.server.ts` with `fetch` stubbed by `vi.stubGlobal`, so it never reaches a registry. It runs the real Shiki highlighter, which works in Node.
- The web-verifier suite (`apps/web-verifier/__tests__`, vitest) is pure too: it tests the registry client `lib/api-registry.ts` with `fetch` stubbed by `vi.stubGlobal` and the busy wait replaced, so it never reaches a registry and never sleeps.
- CI (`.github/workflows/check.yml`) runs what `pnpm check` runs: lint, typecheck and `pnpm test:pure`. That is the whole utils, web-viewer and web-verifier suites, plus each `test:pure` script of api-compile, api-registry and status-page: the files that need no server, database or network. The rest of the api-compile and api-registry suites stay local, since they need the compose stack and Testnet. A new server-free test file in api-compile goes in its `test:pure` file list; in api-registry, in the `include` of `vitest.pure.config.ts`.
